# ADR 0011: The database runs in MVCC mode

Status: accepted (step 7c.1). Changes the concurrency parts of ADR 0005 and
ADR 0007, and how ADR 0006 copies the database.

## Context

ADR 0007 deferred Turso's MVCC (`BEGIN CONCURRENT`): it was thought
experimental, and whether backups still worked under it was unknown. Turso
0.8.4 settles both. MVCC is a plain journal mode (`PRAGMA journal_mode =
'mvcc'`; `experimental_mvcc` is only an old alias), and `VACUUM INTO` works
in it. A probe with 8 writers each committing 50 transactions of 200 rows
took 0.11 s with `BEGIN CONCURRENT` and no retries, against 0.46 s in WAL
mode, where writers queue. The activity logs (step 7c) have several
writers; later, Headscale state and GUI sessions will write next to
configuration saves.

## Decision

- **Every Parallax database runs in MVCC mode.** Opening one switches it
  if it isn't yet (databases from before 7c are in WAL mode); the mode is
  stored in the file, so that happens once. It switches before migrating,
  so every migration runs, and is tested, under MVCC.
- **Configuration changes still go through the daemon's one writer task.**
  Each is validated against the whole configuration, and two concurrent
  validations could each pass and together break a rule that spans rows
  (write skew). That's about correctness, not locking, and MVCC doesn't
  change it. Saves keep `BEGIN IMMEDIATE`, which holds the database's one
  exclusive writer while it runs (milliseconds); what this step adds is
  the ability to write concurrently, for the writers that need it. The
  activity logs (7c.2) get their own database file, so their concurrent
  writers never meet a configuration save.
- **A backup's copy is rebuilt from the rows** (ADR 0006): a new database
  in WAL mode, filled table by table inside one read transaction on a
  second connection to the live one (so nothing else joins it, and
  dropping it ends it), then compacted with `VACUUM INTO`. A file copy won't do: MVCC
  never reuses a deleted row's number, so a save that rewrites rows with
  the same values would give a different file each time, and "skip when
  unchanged" would never skip. Rebuilt, the same rows give the same bytes,
  and the file is one `sqlite3` opens (it can't open an MVCC file).
- **Runtime state isn't backed up.** The copy leaves out the tables a
  restore never reads (`daemon_state`, ADR 0008), so a new public IP isn't
  new contents.
- **Turso's own tables** (`__turso_internal_*`, MVCC's bookkeeping) are
  never copied by a backup or restore.
- MVCC's log (`parallax.db-log`, which holds the latest writes, private
  keys included) is owner-only like the database. Turso names it by
  replacing the extension, so a database not ending in `.db` gets
  `<stem>.db-log`; that's the file secured.

## Consequences

- `sqlite3` can't open the live database; a backup's `parallax.db` it can.
- One process per database, as since ADR 0007: MVCC refuses multi-process
  access.
- Migrations must stay inside what MVCC allows: no `WITHOUT ROWID` tables,
  `REINDEX`, virtual tables or column changes that rebuild an index. The
  migration tests run under MVCC and would catch one.

## Rejected

- **MVCC only for the logs.** Two modes means two open paths and the
  question of which mode a file is in when debugging or restoring, for no
  gain: the configuration database loses nothing it uses.
- **Keeping `VACUUM INTO` of the live file and checksumming the rows
  instead.** The restore check compares the checksum with the payload's
  bytes, so it would need a second checksum and a manifest change, and the
  copy would still be a file `sqlite3` can't open.
